# Spec: Автовыгрузка чатов для «Ловца лидов» (Lead Catcher — авто)

Status: draft (нужны 2 решения перед `ready-for-agent`, см. Open Questions)

Supersedes: `.scratch/telegram-lead-bot/spec.md` строка "Шаг 1 «Ловец лидов» — ручной разовый
инструмент вне бота, не реализуется как часть этой системы" — эта фича добавляет автоматическую
выгрузку туда, где раньше был только ручной экспорт. Сам промпт П1 и разовость («ты сам пишешь
первым») не меняются — меняется только способ получить сырые сообщения.

## Problem Statement

Шаг 1 «Ловец лидов» (урок 01) сейчас требует вручную выгружать историю сообщений из открытой
группы Telegram/VK перед тем, как прогнать промпт П1 «Ловец тёплых лидов». Это разовая ручная
операция, которая не масштабируется на много источников и легко забывается/устаревает.

## Solution

Отдельный модуль (не MCP — обычный клиент внутри процесса) на **отдельных** аккаунтах для
Telegram и VK (не боевой userbot-аккаунт из `telegram-lead-bot`), который по сохранённым ссылкам
на чаты/группы вытаскивает новые сообщения инкрементально, прогоняет их через П1 и складывает
кандидатов в новый раздел веб-CRM. Запуск — только по команде вручную (on-demand), без cron.

## User Stories

1. Как владелец бизнеса, я хочу добавить ссылку на открытую Telegram-группу или VK-сообщество в
   CRM, чтобы система знала, откуда тянуть сообщения.
2. Как владелец бизнеса, я хочу нажать «Выгрузить сейчас» на источнике и получить только новые
   сообщения с прошлого прогона (не всю историю заново), чтобы не дублировать работу и не жечь
   лимиты API.
3. Как владелец бизнеса, я хочу, чтобы каждая новая пачка сообщений автоматически прогонялась
   через промпт П1 «Ловец тёплых лидов», чтобы не запускать это отдельным шагом руками.
4. Как владелец бизнеса, я хочу видеть найденных кандидатов (цитата, повод, ссылка на автора,
   готовый заход) в отдельном разделе CRM `/catcher`, чтобы решать, кому писать первым.
5. Как владелец бизнеса, я хочу вручную отмечать кандидата «написал», чтобы не потерять, кому уже
   написал, а кому ещё нет — система сама никому не пишет первой (ни в Telegram, ни в VK).
6. Как владелец бизнеса, я хочу, чтобы выгрузка использовала отдельные Telegram/VK-аккаунты,
   не связанные с боевым userbot'ом продаж, чтобы риск бана/флуд-лимита не задевал продающий канал.
7. Как разработчик, я хочу, чтобы при `FloodWaitError` (Telegram) или ограничении частоты
   запросов (VK) выгрузка просто ждала указанное время и продолжала, а не падала.

## Implementation Decisions

- **Новые модули**: `catcher_tg.py` (Telethon, отдельная сессия `CATCHER_TG_STRING_SESSION` +
  свои `CATCHER_TG_API_ID`/`CATCHER_TG_API_HASH`), `catcher_vk.py` (`vk_api`, отдельный
  `VK_ACCESS_TOKEN` с правами `wall` на отдельном аккаунте), `catcher_db.py` (новые таблицы),
  `catcher_pipeline.py` (прогон П1 над свежими `raw_messages`).
- **Схема БД** (новые таблицы в той же SQLite, что и боевой бот):
  - `source_chats(id, platform ['tg'|'vk'], url, enabled, last_message_id, last_checked_at)`
  - `raw_messages(id, source_chat_id, external_id, author, text, url, posted_at, fetched_at)`
  - `catch_candidates(id, raw_message_id, quote, reason, contact_url, opener_text, status
    ['new'|'contacted'], created_at)`
- **Инкрементальность**: Telegram — `iter_messages(chat, offset_id=last_message_id,
  reverse=True)`; VK — постраничный `wall.get`/`wall.getComments` с остановкой на первом уже
  виденном `external_id`.
- **CRM**: новый раздел `/catcher` в существующем `crm.py` — список источников (добавить/
  включить/выключить), кнопка «Выгрузить сейчас» (синхронный вызов на запрос, без фоновой
  очереди — MVP), таблица кандидатов со статусом.
- **П1**: переиспользует существующий текст промпта «Ловец тёплых лидов» из
  `materials/Дополнительные материалы к уроку 3.md` — источник правды не меняется, меняется
  только то, что подаётся на вход (не ручной вывод экспорта, а `raw_messages` из БД).
- **Секреты** (новые, отдельно от боевого userbot'а): `CATCHER_TG_API_ID`,
  `CATCHER_TG_API_HASH`, `CATCHER_TG_STRING_SESSION`, `VK_ACCESS_TOKEN` — только в `.env`,
  никогда в коде/коммитах, как и остальные секреты проекта (см. `CLAUDE.md`, раздел «Работа с
  секретами»).

## Testing Decisions

- Юнит-тесты чистой логики: инкрементальный курсор (не тянем уже виденное), маршрутизация
  raw_message → catch_candidate по ответу П1 (парсинг), идемпотентность миграций новых таблиц.
- Реальные вызовы Telethon/vk_api/LLM в тестах не мокаются глубоко — тестируется код вокруг них,
  как в `telegram-lead-bot/spec.md`.

## Out of Scope

- Автоматическая отправка первого сообщения кандидату — по правилам курса и Telegram ToS первым
  всегда пишет человек, бот только готовит заход.
- Расписание/cron — только ручной запуск по кнопке (MVP).
- Более продвинутая защита от банов (ротация аккаунтов/прокси) — только уважение
  `FloodWaitError`/rate-limit ответов.
- Реальный VK OAuth-флоу помощник (аналог `login.py`/`export_session.py` для Telegram) — способ
  получения `VK_ACCESS_TOKEN` см. Open Questions.

## Open Questions (блокируют переход в ready-for-agent)

1. **VK-токен**: получать вручную через официальный OAuth (Implicit Flow — залогиниться новым
   аккаунтом, вставить токен в `.env`), или нужен скрипт-хелпер по аналогии с `login.py`/
   `export_session.py`?
2. **Обработка лимитов**: достаточно ли для MVP просто ждать `FloodWaitError`/VK rate-limit и
   продолжать (без ретраев с бэкоффом сверх этого, без алертов)?

## Comments

- 2026-08-11: спека создана по итогам обсуждения — пользователь хочет не только ручную выгрузку
  чатов ВК/Telegram (шаг 1 «Ловец лидов»), но и автоматическую по сохранённым ссылкам. Context7
  подтвердил техническую возможность: Telethon `iter_messages` читает историю публичного чата по
  ссылке через MTProto-сессию; `vk_api` читает `wall.get`/комментарии открытой группы через
  токен. Решено: отдельные аккаунты Telegram и VK (не боевой userbot), запуск on-demand (не
  cron), результат — новый раздел веб-CRM `/catcher`, а не файл на диск.
