# ТЗ: Telegram-бот продаж + движок расчёта КП + производственная очередь + веб-CRM (SMB)

Обезличенное техническое задание на систему автоматизации SMB, который **продаёт готовое
и изготавливает под заказ**. Все секреты и идентификаторы — плейсхолдеры вида `<...>`.
Предметная область в примерах — «продажа товаров/услуг + изготовление изделий на заказ»
(напр. корпусная мебель, металлоизделия, окна), но **всё конфигурируемо** (см. «Настраиваемые
входы»). Стек: Telegram (Telethon MTProto + Bot API), OpenAI-совместимый LLM, SQLite, веб-CRM
на стандартной библиотеке Python, деплой на PaaS-контейнер (напр. Amvera).

---

## 0. Управляющий принцип

**LLM — оркестратор, код — источник истины по числам.** Любое число (цена, КП, приоритет,
дата, ориентир) вычисляется детерминированно в коде по формулам и справочникам. LLM только:
(а) понимает намерение и сортирует лида; (б) матчит свободный текст на позицию/техкарту или
собирает состав сметы из справочника; (в) формулирует ответ человеку. **LLM никогда не
выдумывает цену, срок или наличие.** Нет данных — не сочиняем.

---

## 1. Назначение

Автоматизировать полный путь **откликнувшегося лида**: оценить намерение → прогреть →
рассчитать предложение (в т.ч. **КП на изготовление под заказ**) → довести до оплаты →
поставить **производственную задачу** и вести её очередь по приоритету → синхронизировать
статусы и уведомлять клиента. Всё голосом бизнеса, человекоподобно. Греть **только тех, кто
сам написал** или проявил интерес в группах; холодную базу не трогать.

**Принципы:** балл лида в моменте (картотеку не ведём); деградация без LLM (эвристика/шаблоны);
безопасные дефолты (сухой прогон до ручной обкатки); числа — из кода/справочников.

---

## 2. Каналы и роли

| Роль | Реализация | Зачем |
|---|---|---|
| **Продавец (userbot)** | Telegram **user-аккаунт**, MTProto (Telethon) | Читает личку и группы, скорит, греет, эскалирует, называет ориентир. Bot API так не может. |
| **Кассир (bot)** | Telegram **бот** (Bot API) | Оплата: инлайн-кнопки, callback, приём «Оплатил». Userbot кнопки не умеет. |
| **CRM (web)** | HTTP-сервер (stdlib) | Заявки, движение статусов, **очередь производства**, уведомления клиенту. |

**Всё в одном процессе**, чтобы делить одну SQLite. Отдельные процессы/контейнеры SQLite-файл
не делят (иначе нужен общий Postgres).

---

## 3. Архитектура

Один процесс (asyncio) поднимает параллельно:
1. `user_client` — userbot (MTProto) по строке-сессии;
2. `bot_client` — бот-кассир по токену BotFather;
3. веб-CRM — HTTP-сервер в фоновом потоке (та же БД);
4. фон: планировщик догрева, цикл напоминаний об оплате.

Модуль расчёта/производства — **библиотека в том же процессе и той же БД** (не отдельный
сервис), вшивается в обработчик эскалации и в CRM.

```
Telegram ──(личка/группы)──► userbot ──► П1 скоринг ──► действие
                                              │
              ┌───────────────┬───────────────┼────────────────┐
            skip            warm           warm+вопрос         escalate(🌋)
           (молчим)     касание П5      о цене кастома        заявка в CRM
                                        │                      │
                              ОРИЕНТИР «от ~X ₽»      маршрутизация: услуга→сервис,
                              (read-only расчёт КП)   товар в прайсе→склад,
                                                      нет в прайсе→ПРОИЗВОДСТВО
                                                      │
                                        синхронный расчёт КП → orders.price,
                                        создание производственной задачи
                                                      │
                              userbot шлёт лиду deep-link на бота-кассира
                                                      ▼
Telegram ─(лид жмёт ссылку)─► бот-кассир ─► карточка оплаты + [Оплатил] ─► paid
                                                      ▼
                          CRM /production: очередь по приоритету,
                          мастер двигает этапы ─► статус заявки синхронится ─► уведомление лиду
```

## 4. Функциональные требования — продажи и прогрев

### 4.1. Режим 1 — обработка входящего (событие)

На каждое входящее (личка или сигнал в группе), по порядку:
1. **Проверка безопасности** (см. 4.11) — до всего.
2. **Вопрос о статусе заявки?** (см. 4.10) — если у лида есть заказ и текст похож на вопрос
   о статусе — ответить по данным заказа и выйти.
3. **Скоринг П1** — LLM-судья 0–100 (JSON: балл, этап воронки, icebreaker, причина).
4. **Действие по бэнду:**

| Балл | Бэнд | Действие |
|---|---|---|
| 0–19 | ❄️ cold | не трогать |
| 20–39 | 🌤 cool | касание П5 (мягче) |
| 40–59 | ☀️ warm | касание П5 (предметно) |
| 60–79 | 🔥 hot | касание П5 (ближе к CTA) |
| 80–100 | 🌋 boiling | **эскалация** (4.3), дальше не греем |

5. Для «warm»-действия: если лид **спрашивает цену кастома** — вместо обычного касания дать
   **ориентировочную сумму** (4.5). Иначе — обычное касание П5.
6. Обновить контекст диалога и этап воронки.

**Группы:** реагировать только на **слова-сигналы** покупки (грубый пре-фильтр), финально решает
П1. Режим ответа настраивается: `off` | `reply` | `dm`.

### 4.2. Режим 2 — догрев затихших (расписание)

Раз в сутки: активные «затихшие» лиды → по **порогу тишины** следующий (каждый раз другой)
шаг расписания:

| Порог тишины | Шаг | Смысл | Тон |
|---|---|---|---|
| ≥ 1 день | 1 «польза» | полезное касание без CTA | заботливый эксперт |
| ≥ 3 дня | 2 «доверие» | кейс похожего клиента + вопрос-крючок | дружелюбный |
| ≥ 7 дней | 3 «мягкий дедлайн» | «ещё актуально?» + конкретика | деловой, финальный |

Правила: шаг 1→2→3, на 3 стоп (не по кругу); новое входящее сбрасывает цикл; минимальный
зазор между касаниями (напр. 20 ч); эскалированных/заблокированных не греем.

### 4.3. Эскалация → заявка → маршрутизация → оплата

При 🌋:
1. **Определить позицию заказа** из диалога (LLM выбирает позицию прайса + `in_price`, либо «под заказ»).
2. **Создать заявку** (позиция, категория, цена, отдел, статус `new`, этап воронки).
3. **Маршрутизация в отдел:**
   - услуга → **сервис**;
   - товар есть в прайсе (в наличии) → **склад**;
   - товара нет в прайсе (под заказ/изготовление) → **производство**.
4. **Если отдел = производство:** синхронно рассчитать **КП** (см. 5) → записать `orders.price`
   расчётной ценой → создать **производственную задачу**. Если КП не собрать → `needs_estimator`,
   цену ставит технолог в CRM (лиду обещаем смету, ссылку на оплату не шлём).
5. Сформировать **ссылку на оплату** с реальной ценой: `<PAY_URL>?order=<id>&amount=<цена>`.
6. **Увести лида к боту-кассиру** deep-link'ом `t.me/<bot>?start=order_<id>` (бот не пишет первым).
7. Продублировать карточку эскалации оператору.

### 4.4. Оплата (бот-кассир)

1. deep-link → бот показывает **карточку заказа** + инлайн-кнопку **«Оплатил ✅»**; заявка →
   `awaiting_payment`, старт «часов напоминаний».
2. Нажатие «Оплатил» → callback → `paid`, воронка++.
3. Бот шлёт **инструкцию «что дальше»** по отделу (сервис / склад / производство).

### 4.5. Ориентировочная сумма для кастома (read-only)

Тёплый лид спрашивает цену изделия под заказ (детект по ключевым словам «сколько стоит /
цена / расчёт / прикинуть»), а позиции нет в прайсе (→ производство):
1. Рассчитать **ориентир** движком КП (см. 5) — **read-only**, БЕЗ создания заявки/задачи.
2. Ответить «**ориентировочно от ~X ₽** за базовую комплектацию» (число округлить вниз до сотен —
   честный «от»; кастом по размеру только дороже) + мягко предложить замер/уточнение для точной сметы.
3. Число берётся из расчёта, не выдумывается. Не собрать смету → честно предложить замер.

### 4.6. Напоминания об оплате

Лесенка с момента показа карточки (или создания заявки — в агентском режиме):

| Порог | Действие |
|---|---|
| +30 мин | «заявка отправлена, посмотрите — получили ли» |
| +1 день | «рекомендуем оплатить: смета/цена зафиксирована ограниченный срок» |
| +3 дня | «заявка закроется через 30 минут» |
| +3 дня 30 мин | **автозакрытие** (`cancelled`) + уведомление |

Оплата на любом шаге останавливает цепочку. **Бот включён** → шлёт бот шаблоном; **бот выключен**
→ шлёт userbot живым текстом от LLM.

## 5. Движок расчёта КП (детерминированный)

### 5.1. Справочники (нормативы)

- **Материалы**: `код → (наименование, единица, цена за единицу)`.
- **Работы (операции)**: `код → (наименование, единица, ставка руб/час)`.
- **Технологические карты** (типовые изделия): `{ артикул, наименование, габариты,
  BOM: [(код_материала, норма_расхода)], операции: [(код_работы, норма_часов)] }`.

Источник — таблицы (Excel/CSV) ИЛИ **текстовый модуль-фолбэк** (Python-литералы) для деплоя без
бинарников (см. грабли деплоя). Загружаются один раз, кэшируются в памяти.

### 5.2. Формула КП (в коде, всегда)

```
Материалы      = Σ(норма_расхода × цена_материала)
Работы         = Σ(норма_часов × ставка)
Прямые         = Материалы + Работы
Накладные      = Прямые × <НАКЛАДНЫЕ_%>          # напр. 15%
Себестоимость  = Прямые + Накладные
Наценка        = Себестоимость × <НАЦЕНКА_%>     # напр. 35%
Отпускная цена = Себестоимость + Наценка         # это и есть КП (orders.price)
```
Смета (строки материалов/работ + промежуточные итоги + %) сохраняется в `kp_json` задачи.

### 5.3. Как собирается состав сметы

Функция `compose_kp(текст_изделия)`:
1. **Матч на техкарту** по названию (эвристика/консервативный матч; неоднозначность → пропуск,
   чтобы не занизить цену) → берём готовый BOM+операции карты.
2. Нет матча + доступен LLM → **LLM собирает состав** из справочника (выбирает коды материалов/
   работ и нормы). **Каждая строка валидируется против справочника** — код обязан существовать;
   выдуманное отбрасывается.
3. Нет матча и нет/пусто LLM → вернуть `None` → задача помечается **`needs_estimator`** (цену
   ставит технолог в CRM вручную).

Тот же `compose_kp` используется и для **синхронного КП при эскалации** (пишет цену), и для
**read-only ориентира** (4.5, ничего не пишет).

## 6. Производственная очередь и приоритизация

### 6.1. Производственная задача

Создаётся из оплачиваемой/эскалированной заявки с `destination='производство'`. Поля: связь с
заявкой, позиция, артикул матч-карты, `kp_json` (смета), цена, часы работы, маржа (руб.), дата
сдачи, `priority_score`, этап, ответственный, `needs_estimator`, плановый старт, тайминги.

### 6.2. Приоритет и планирование (в коде)

- **Priority Score** = (маржа ÷ часы работы) × **коэффициент срочности**(дата сдачи, сегодня,
  `<K_СРОЧНОСТИ>`). Чем ближе срок — тем выше. Нет даты сдачи → коэффициент = 1 (нейтрально).
  (Это EDD/WSPT, взвешенный маржой на узком месте — см. принцип узкого места.)
- **Обратное планирование**: `плановый_старт` = от даты сдачи назад с буфером на этап
  (`<БУФЕР_ЭТАПА_ЧАСОВ>`). Планируем от даты сдачи, а не от свободного слота.
- Очередь сортируется по `priority_score` убыв. Пересчёт при постановке задачи, смене даты сдачи,
  движении этапа.

### 6.3. Этапы и стыковка со статусами заявки

Свёрнутый производственный трек: **Очередь → Заготовка → Сборка → Контроль → Готово**.
Маппинг на статус заявки (виден лиду): промежуточные этапы → `in_progress`; «Готово» → `ready`.
При переходе этапа CRM синхронно двигает `orders.status` и **уведомляет лида** (Bot API).

## 7. Веб-CRM

Мини-CRM в том же процессе, та же БД, на домене проекта, доступ по `?token=<секрет>`. Минимализм.

**Раздел «Заявки»:**
- `GET /` — список заявок (№, лид, позиция, цена, отдел, статус, кнопка сдвига статуса).
- `GET /api/orders` — JSON заявок (+ инфо о лиде).
- `POST /api/advance?id=N` — сдвинуть статус + уведомить лида.

**Раздел «Производство» (`GET /production`):**
- очередь производственных задач, отсортированная по Priority Score;
- **легенда-пояснение** (что такое Score, «Старт»/обратное планирование, этапы);
- по задаче: **кнопка движения этапа** (`POST /api/prod_advance?id=N`) и **поле даты сдачи**
  (`POST /api/prod_due?id=N&due=YYYY-MM-DD` → пересчёт приоритета/старта);
- `needs_estimator`-задачи помечены (цену ставит технолог).

**Путь статусов заявки (виден лиду):** `Оплачено → В работе → Готово → Выдано`; при смене — уведомление.
**Демо-инструменты (только за токеном):** `POST /api/reset` (полный сброс БД, включая задачи),
`POST /api/seed_prod` (засеять тестовые заявки производства с расчётом КП). Убрать в реальном проде.

**Безопасность вывода:** любые пользовательские строки (позиция и т.п.) HTML-экранировать (XSS).

## 8. Ответы о статусе и защита

### 8.1. Ответы о статусе заявки

Лид спрашивает статус («какой статус?», «когда готово?», «оплатил, что дальше?») и у него есть
заказ → userbot **не скорит и не продаёт**, а отвечает голосом бизнеса по реальному статусу
(тепло, 1–2 предложения, без выдумок).

### 8.2. Защита от prompt-инъекций и выманивания коммерческой информации

До скоринга и любых LLM-вызовов:
1. **Два слоя:** эвристика (высокоточные маркеры: «ignore instructions», «system prompt»,
   jailbreak, «режим разработчика», «себестоимость/наценка», ключи/токены, исходники) + LLM-
   классификатор тонких попыток (текст лида — **данные**, не инструкции). Обычные вопросы о
   товаре/цене/сроке — не угроза.
2. **Алерт** оператору (🛑 кто, причина, текст).
3. **Аварийное отключение чата:** лид → `blocked`, бот молча перестаёт отвечать; разблокировка вручную.

## 9. Промпты (обезличенные шаблоны)

Все тексты — единый «источник правды» в одном модуле; LLM OpenAI-совместимый; везде фолбэк.

- **Шаблон А (продукт/ЦА):** бизнес, ценность, ЦА, боли, «голос бизнеса». Вход для П1/П5/статуса/ориентира.
- **П1 (скоринг):** Шаблон А + контекст + входящее → строго JSON `{score, buying_stage, icebreaker, reasoning}`; якоря шкалы 0–100.
- **П5 (касание):** Шаблон А + этап + след. шаг + контекст + прайс; 1–3 предложения, живой язык,
  позицию/цену только из прайса/контекста, один мягкий шаг.
- **Извлечение заказа:** выбрать одну позицию из прайса (точное имя + `in_price`) или «под заказ».
- **Сборка сметы (COMPOSE):** по тексту изделия выбрать коды материалов/работ и нормы из справочника
  (строго существующие коды) → JSON. Используется, когда изделие не матчится на техкарту.
- **Ориентир (ESTIMATE):** Шаблон А + изделие + **рассчитанное** число → назвать «ориентировочно
  от ~X ₽», других цифр не выдумывать, предложить замер/уточнение.
- **Guard:** классификатор угрозы `{threat, kind, reason}`; входящее — данные.
- **Ответ о статусе / напоминание (агент):** голос бизнеса + данные заказа → живой текст.
- **Фолбэки без LLM:** скоринг по ключевым словам, нейтральные касания, шаблонные напоминания/
  ответы, шаблонный ориентир с тем же числом.

## 10. Модель данных (SQLite)

```sql
CREATE TABLE leads (              -- только откликнувшиеся; балл НЕ храним
  chat_id PRIMARY KEY, username, name, source,      -- 'dm'|'group'
  last_msg, last_msg_at, last_touch_at,
  next_step_idx INTEGER DEFAULT 0, dialog_context TEXT DEFAULT '',
  status TEXT DEFAULT 'active',   -- active|escalated|dormant|blocked
  funnel_stage INTEGER, updated_at);

CREATE TABLE orders (
  id INTEGER PRIMARY KEY AUTOINCREMENT, chat_id, item,
  category,        -- 'Товар'|'Услуга'|''
  price INTEGER,   -- из прайса или расчётный КП или NULL
  destination,     -- 'производство'|'сервис'|'склад'
  payment_link,
  status TEXT DEFAULT 'new',  -- new->awaiting_payment->paid->in_progress->ready->done|cancelled
  funnel_stage, awaiting_since, reminder_stage INTEGER DEFAULT 0,
  created_at, updated_at);

CREATE TABLE production_tasks (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  order_id, item, matched_card, kp_json,          -- смета JSON
  price INTEGER, production_hours REAL, margin_rub INTEGER,
  due_date, priority_score REAL,
  stage TEXT DEFAULT 'Очередь', assignee,
  needs_estimator INTEGER DEFAULT 0, planned_start,
  created_at, updated_at);

CREATE TABLE handoff (id PK AUTOINCREMENT, chat_id, payload, created_at, delivered INTEGER DEFAULT 0);
CREATE TABLE meta (key PRIMARY KEY, value);
```
Миграции идемпотентные (`CREATE TABLE IF NOT EXISTS`, `PRAGMA table_info` + `ALTER TABLE`).

## 11. Настраиваемые входы (на другой бизнес)

## 13. Деплой (PaaS-контейнер, напр. Amvera)

- **Один процесс** (`main.py`), постоянный диск в `/data` (SQLite).
- **Веб-CRM** на домене проекта → `containerPort: 80`, слушать `0.0.0.0:80`; при необходимости
  завести бесплатный домен.
- **Регион** ближе к стабильному доступу к Telegram. RAM ≥ ~0.5 ГБ (два клиента + веб + LLM).
- **StringSession для облака:** интерактивный ввод кода в контейнере невозможен → локально войти
  один раз (телефон+код), экспортировать сессию в строку (**без сети** — только чтение файла),
  положить в `TG_STRING_SESSION` (secret).
- **Нормативы без бинарников:** если удалённая среда/загрузчик не видит локальный диск и/или
  ненадёжно передаёт бинарники — вшить нормативы **текстовым модулем** (Python-литералы) и грузить
  из него, когда Excel рядом нет. Весь деплой — только текстовые файлы.
- **Заливка + целостность:** файлы заливать текстом; после заливки **сверять SHA256** (скачать и
  сравнить). Пересборка = **боевой рестарт** живого userbot (короткий даунтайм) — подтверждать.

## 14. Нефункциональные требования

- **Безопасность:** секреты только в env; текст лида в LLM — данные; блок инъекций; CRM за токеном;
  HTML-экранирование вывода CRM; не логировать секреты.
- **Наблюдаемость:** INFO-логи ключевых событий (логин, входящее+балл, эскалация, КП посчитан,
  ориентир, оплата, напоминание, движение этапа, блок-инъекция).
- **Деградация:** без LLM — эвристика/шаблоны + матч техкарт/`needs_estimator`; без бота —
  напоминания шлёт userbot; без прайса — П5 без цен. **Числа никогда не выдумывать.**
- **Идемпотентность:** миграции, «часы» напоминаний, шаги догрева, постановка задач — без дублей.

- **Юнит-тесты чистой логики** (без Telegram/LLM): бэнды, выбор шага догрева, тишина, парсинг JSON,

- **CLI обкатки:** «входящее → П1 → касание/эскалация» без Telegram; батч-расчёт КП по новым заявкам.

## 16. Эксплуатационные грабли (обязательно учесть)

- **SQLite не в облачно-синхронизируемой папке** (Dropbox/Я.Диск) — блокировки/повреждение. Держать
  в `/data` на PaaS.
- **Один экземпляр userbot на сессию.** Одна сессия с двух IP → Telegram аннулирует ключ
  (`AuthKeyDuplicatedError`), лечится только новой StringSession. Рестарты разносить; не подключать
  сессию локально, пока работает облако.
- **Инлайн-кнопки — только у бота, не у userbot.** Оплата/кнопки — в боте-кассире (deep-link).
- **Бот не пишет первым** — лид жмёт Start (deep-link).
- **Отдельный PaaS-проект не делит SQLite** — бот + CRM + движок КП в одном процессе, либо Postgres.
- **Удалённая заливка бинарников ненадёжна** — нормативы текстом; проверять SHA256.
- **Пересборка перезапускает живой userbot** — подтверждать; держать безопасный откат (реверт коммитов + rebuild).

## 17. Состав модулей (ориентир)

| Модуль | Ответственность |
|---|---|
| `main.py` | запуск (userbot + бот + CRM + фон), Режим 1/2, эскалация, мост к движку КП, ориентир |
| `pipeline.py` | П1, П5, извлечение заказа, guard-классификатор, ответ о статусе, детект ценового интента, генератор ориентира |
| `prompts.py` | все промпты/шаблоны (единый источник правды) |

| `bot.py` | бот-кассир: deep-link, карточка оплаты, callback, «что дальше» |
| `reminders.py` | лесенка напоминаний (бот/агент) |
| `guard.py` | эвристика + LLM-классификатор инъекций |
| `crm.py` | веб-CRM (заявки + раздел «Производство», статусы, уведомления, сброс/сид) |

| **`norms.py` / `norms_data.py`** | загрузка нормативов (материалы/работы/техкарты) + текстовый фолбэк |
| **`kp.py`** | расчёт КП: формула, матч техкарты, LLM-сборка состава, валидация |
| **`priority.py`** | Priority Score + обратное планирование |
| **`production_db.py`** | таблица `production_tasks`, миграции, CRUD, пересчёт приоритетов, сброс |
| **`production_crm.py`** | рендер очереди производства + движение этапов + дата сдачи |
| **`production_prompts.py`** | промпты сборки сметы / объяснений |
| **`poller.py`** | обработка новых заявок производства (расчёт КП → задачи) |
| `login.py`, `export_session.py` | разовый логин и экспорт StringSession |
| `tests` | юнит + интеграция чистой логики |
