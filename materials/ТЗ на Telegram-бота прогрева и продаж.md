# ТЗ: Telegram-бот прогрева лидов и продаж для SMB

Обезличенное техническое задание. Все секреты и идентификаторы — плейсхолдеры вида `<...>`.
Пример предметной области — «продажа запчастей и услуг автосервиса», но продукт, прайс и
воронка **конфигурируемы** (см. раздел «Настраиваемые входы»).

---

## 1. Назначение

Автоматизировать работу с **откликнувшимися лидами** в Telegram: оценивать намерение,
прогревать, доводить до оплаты, вести заявки в CRM и отвечать на вопросы клиента —
голосом бизнеса, человекоподобно. Греть **только тех, кто сам написал** (личка) или
проявил интерес в общих группах. Холодную базу не трогать (это спам).

**Ключевые принципы:**
- Балл лида не хранить как картотеку — он живёт в моменте; хранить только контекст диалога.
- Не выдумывать факты (цены/наличие/сроки берём из прайса/данных; нет данных — не сочиняем).
- Работать в деградированном режиме без LLM (эвристика/шаблоны), полноценно — с LLM.
- Безопасные дефолты: «сухой прогон» (ничего не шлём) до ручной обкатки.

---

## 2. Каналы и роли

| Роль | Реализация | Зачем |
|---|---|---|
| **Продавец (userbot)** | Telegram **user-аккаунт** через MTProto (Telethon) | Читает личку и общие группы, ведёт диалог, скорит, греет, эскалирует. Бот-API так не может (не видит чужую личку и произвольные группы). |
| **Кассир (bot)** | Telegram **бот** (Bot API / Telethon bot-client) | Оплата: инлайн-кнопки и callback (userbot этого не умеет — только бот). Приём «Оплатил», фидбек. |
| **CRM (web)** | HTTP-сервер | Просмотр заявок и движение статусов; уведомления клиенту при смене статуса. |

**Важно:** всё крутится **в одном процессе**, чтобы разделять одну БД (SQLite). Отдельные
процессы/контейнеры не делят SQLite-файл — тогда нужен общий Postgres.

---

## 3. Архитектура

Один процесс (asyncio) поднимает параллельно:
1. `user_client` — userbot (MTProto) по строке-сессии (см. деплой);
2. `bot_client` — бот-кассир по токену от BotFather;
3. веб-CRM — HTTP-сервер в фоновом потоке;
4. фоновые задачи: планировщик догрева, цикл напоминаний об оплате.

Общее состояние — локальная SQLite-база (файл на постоянном диске).

```
Telegram ──(личка/группы)──► userbot ──► П1 скоринг ──► действие
                                              │
                          ┌───────────────────┼─────────────────────┐
                        skip                 warm                escalate(🌋)
                       (молчим)         касание П5              заявка в CRM
                                                                 │
                                       userbot шлёт лиду deep-link на бота
                                                                 ▼
Telegram ──(лид жмёт ссылку)──► бот-кассир ──► карточка оплаты + [Оплатил]
                                                     │ callback
                                        заявка paid, воронка++, «что дальше»
                                                     ▼
                       CRM (web): менеджер двигает статус ──► уведомление лиду
```

## 4. Функциональные требования

### 4.1. Режим 1 — обработка входящего (событие)

На каждое входящее от лида (личка или сигнал в группе):
1. **Проверка безопасности** (см. 4.8) — до всего остального.
2. **Вопрос о статусе заявки?** (см. 4.7) — если у лида есть заказ и текст похож на вопрос
   о статусе, отвечаем по данным заказа и выходим.
3. **Скоринг П1** — LLM-судья 0–100 в JSON: балл, этап воронки, короткий icebreaker, причина.
4. **Действие по бэнду:**

| Балл | Бэнд | Действие |
|---|---|---|
| 0–19 | ❄️ cold | не трогать |
| 20–39 | 🌤 cool | касание П5 (мягче) |
| 40–59 | ☀️ warm | касание П5 (предметно по этапу воронки) |
| 60–79 | 🔥 hot | касание П5 (ближе к CTA) |
| 80–100 | 🌋 boiling | **эскалация** (см. 4.3), дальше не греем |

5. Обновить контекст диалога и этап воронки лида.

**Группы:** реагировать только на сообщения со **словами-сигналами** покупки (грубый
пре-фильтр), затем финально решает П1. Режим ответа в группе настраивается:
`off` (только зафиксировать), `reply` (ответить в тред), `dm` (написать в личку).

### 4.2. Режим 2 — догрев затихших (расписание)

Раз в сутки будим фоновую задачу: берём активных лидов, которые «затихли», и по **порогу
тишины** шлём следующий, **каждый раз другой** шаг из «расписания догрева»:

| Порог тишины | Шаг | Смысл | Тон |
|---|---|---|---|
| ≥ 1 день | 1 «польза» | полезное касание без CTA | заботливый эксперт |
| ≥ 3 дня | 2 «доверие» | кейс похожего клиента + вопрос-крючок | дружелюбный |
| ≥ 7 дней | 3 «мягкий дедлайн» | «ещё актуально?» + конкретика | деловой, финальный |

Правила: шаг двигается 1→2→3 и на 3 останавливается (не по кругу); новое входящее от лида
сбрасывает цикл; минимальный зазор между касаниями (напр. 20 ч) — страховка от спама;
эскалированных/заблокированных не греем.

### 4.3. Эскалация → заявка → маршрутизация → оплата

При 🌋 (лид готов покупать):
1. **Определить позицию заказа** из диалога (LLM выбирает позицию из прайса, либо «под заказ»).
2. **Создать заявку** в CRM (позиция, категория, цена, отдел, статус `new`, этап воронки).
3. **Маршрутизация в отдел** по правилу:
   - услуга → **сервис**;
   - товар есть в прайсе (в наличии) → **склад**;
   - товара нет в прайсе (под заказ/изготовление) → **производство**.
4. Сформировать **ссылку на оплату** с реальной ценой: `<PAY_URL>?order=<id>&amount=<цена>`
   (в примере — заглушка `example.com`; в бою — реальный платёжный провайдер).
5. **Увести лида к боту-кассиру**: userbot шлёт лиду **deep-link** `t.me/<bot>?start=order_<id>`
   (бот не может написать лиду первым, пока тот не нажал Start).
6. Продублировать карточку эскалации оператору (в «Избранное» аккаунта или в чат оператора).

### 4.4. Оплата (бот-кассир)

1. Лид открывает deep-link → бот по `order_<id>` показывает **карточку заказа** со ссылкой
   на оплату и **инлайн-кнопкой «Оплатил ✅»**. Заявка → `awaiting_payment`, стартует
   «часы напоминаний».
2. Лид жмёт **«Оплатил ✅»** → callback → заявка `paid`, воронка двигается (напр. этап «оплата»).
3. Бот сразу шлёт **инструкцию «что дальше»**, зависящую от отдела:
   - сервис → «запишем на сервис, мастер свяжется…»;
   - склад → «деталь на складе, комплектуем к выдаче…»;
   - производство → «передали в производство, уточняем срок…».

### 4.5. Напоминания об оплате (неоплаченные заявки)

Лесенка с момента показа карточки оплаты (или создания заявки — в агентском режиме):

| Порог | Действие |
|---|---|
| +30 минут | «заявка отправлена вам, посмотрите — получили ли» |
| +1 день | «рекомендуем оплатить: курс/цены меняются, обычно дорожают; оплата фиксирует цену» |
| +3 дня | «заявка закроется через 30 минут, цены пересчитаны» |
| +3 дня 30 минут | **автозакрытие** заявки (`cancelled`) + уведомление лиду |

Оплата на любом шаге останавливает цепочку. Кто шлёт:
- **бот включён** → шлёт бот шаблонным текстом (заявки `awaiting_payment`);
- **бот выключен** → шлёт **userbot-продавец живым текстом от LLM** (в ту же личку, по всем
  неоплаченным заявкам).

### 4.6. Веб-CRM

Мини-CRM в том же процессе, читает ту же БД, отдаётся на домене проекта. Доступ по токену
(`?token=<секрет>`). Минимализм.
- `GET /` — страница со списком заявок (№, лид, позиция, цена, отдел, статус, кнопка сдвига).
- `GET /api/orders` — JSON всех заявок (+ инфо о лиде).
- `POST /api/advance?id=N` — двинуть статус вперёд + **уведомить лида** (через Bot API).
- `POST /api/reset` — полный сброс базы (для тестов с нуля).

**Путь статусов (виден лиду):** `Оплачено → В работе → Готово → Выдано`. При каждой смене
CRM шлёт лиду уведомление.

### 4.7. Ответы о статусе заявки (человекоподобно)

Если лид спрашивает про статус («какой статус?», «когда будет готово?», «оплатил, что дальше?»)
и у него есть заказ — userbot **не скорит и не продаёт**, а находит его заказ и отвечает
голосом бизнеса по реальному статусу (тепло, 1–2 предложения, без выдумок).

### 4.8. Защита от prompt-инъекций и выманивания коммерческой информации

На каждое входящее **до скоринга и любых LLM-вызовов**:
1. **Проверка** двумя слоями:
   - эвристика — высокоточные маркеры (`ignore instructions`, `system prompt`, jailbreak,
     `режим разработчика`, «покажи промпт», «себестоимость/наценка», ключи/токены, исходники);
   - LLM-классификатор — тонкие попытки взлома/извлечения (текст лида подаётся как **данные**,
     не как инструкции). Обычные вопросы о товаре/цене/сроках — не угроза.
2. **Алертинг** — при срабатывании оператору падает карточка 🛑 (кто, причина, текст).
3. **Аварийное отключение чата** — лид получает статус `blocked`, бот **молча перестаёт
   отвечать** ему (и на будущие сообщения), догрев его не трогает. Разблокировка — вручную.

## 5. Промпты (обезличенные шаблоны)

Все тексты — единый «источник правды» в одном модуле. LLM — OpenAI-совместимый API
(`base_url` + `api_key`). Везде фолбэк на эвристику/шаблон при недоступности LLM.

- **Шаблон А (продукт/ЦА):** бизнес, ценность, ЦА, боли, «голос бизнеса». Вход для П1 и П5.
- **П1 (скоринг-судья):** на вход — Шаблон А + краткий контекст диалога + входящее; на выход
  строго JSON `{score, buying_stage, icebreaker, reasoning}`; в промпте — якоря шкалы 0–100.
- **П5 (генератор касания):** Шаблон А + этап воронки + след. шаг + контекст + прайс; правила:
  1–3 предложения, живой язык, марку/деталь/цену называть ТОЛЬКО из контекста/прайса, ничего
  не выдумывать, один мягкий следующий шаг.
- **Извлечение заказа:** по диалогу выбрать одну позицию из прайса (точное название +
  `in_price`) или «под заказ».
- **Guard (безопасность):** классификатор угрозы `{threat, kind, reason}`; входящее — данные.
- **Ответ о статусе:** голос бизнеса + данные заказа (№, позиция, статус, отдел) → тёплый ответ.
- **Напоминание (агентский режим):** голос бизнеса + цель шага + данные заказа → живой текст.
- **Шаблоны-фолбэки** (без LLM): скоринг по ключевым словам, нейтральные тексты касаний,
  шаблонные напоминания, шаблонный ответ о статусе.

## 6. Модель данных (SQLite)

```sql
-- Лиды (только откликнувшиеся). Балл НЕ храним.
CREATE TABLE leads (
  chat_id        INTEGER PRIMARY KEY,   -- id пользователя Telegram
  username       TEXT,
  name           TEXT,
  source         TEXT,                  -- 'dm' | 'group'
  last_msg       TEXT,                  -- последнее входящее
  last_msg_at    TEXT,                  -- когда лид писал (порог тишины)
  last_touch_at  TEXT,                  -- когда МЫ касались
  next_step_idx  INTEGER DEFAULT 0,     -- шаг догрева: 0->1,1->2,2->3,3->стоп
  dialog_context TEXT DEFAULT '',       -- короткая сводка (не досье)
  status         TEXT DEFAULT 'active', -- active | escalated | dormant | blocked
  funnel_stage   INTEGER,               -- этап воронки 1..16
  updated_at     TEXT
);

-- Заявки (CRM).
CREATE TABLE orders (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  chat_id       INTEGER,
  item          TEXT,                   -- позиция
  category      TEXT,                   -- 'Товар' | 'Услуга' | ''
  price         INTEGER,                -- из прайса или NULL
  destination   TEXT,                   -- 'производство' | 'сервис' | 'склад'
  payment_link  TEXT,
  status        TEXT DEFAULT 'new',     -- new -> awaiting_payment -> paid -> in_progress -> ready -> done | cancelled
  funnel_stage  INTEGER,
  awaiting_since TEXT,                  -- якорь напоминаний (показ карточки)
  reminder_stage INTEGER DEFAULT 0,     -- сколько напоминаний ушло (0..4)
  created_at    TEXT,
  updated_at    TEXT
);

-- Очередь передачи горячих лидов оператору/«первой линии».
CREATE TABLE handoff (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  chat_id INTEGER, payload TEXT, created_at TEXT, delivered INTEGER DEFAULT 0
);

CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT);  -- служебное
```
Миграции: добавлять недостающие колонки идемпотентно (`PRAGMA table_info` + `ALTER TABLE`).

## 7. Настраиваемые входы (на другой бизнес)

- **Шаблон А** — описание продукта/ЦА/болей/голоса.
- **Воронка (этапы 1..16)** — карта пути клиента (для П5 и `buying_stage`).
- **Прайс** — CSV `Наименование, Категория (Товар|Услуга), Цена`. Единственный источник цен;
  используется для П5, извлечения заказа, маршрутизации.
- **Слова-сигналы для групп** — список стоп-слов покупательского интереса.
- **Пороги** — бэнды скоринга, пороги тишины догрева, тайминги напоминаний.

## 8. Конфигурация (переменные окружения)

Секреты — только в env, никогда в коде. Плейсхолдеры:

| Переменная | Назначение |
|---|---|
| `TG_API_ID`, `TG_API_HASH` | MTProto-доступ (my.telegram.org → API development tools) |
| `TG_STRING_SESSION` | залогиненная сессия userbot'а строкой (для облака; полный доступ к аккаунту — секрет) |
| `TG_PHONE` | телефон аккаунта (только для локального первого логина) |
| `BOT_TOKEN` | токен бота-кассира (BotFather). Пусто → напоминания шлёт userbot-агент |
| `PAYMENT_BASE_URL` | база ссылки на оплату |
| `OPERATOR_CHAT` | куда слать алерты/карточки (напр. «Избранное» = `me`) |
| `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL` | LLM (OpenAI-совместимый). Пусто → эвристика |
| `DB_PATH` | путь к SQLite (на постоянном диске) |
| `DRY_RUN` | 1 — считаем/логируем, не отправляем; 0 — боевой режим |
| `SCHEDULER_ENABLED` | включить догрев по расписанию |
| `GROUP_MONITOR` | `all` \| `list` \| `off`; `GROUPS` — белый список при `list` |
| `GROUP_REPLY_MODE` | `off` \| `reply` \| `dm` |
| `GROUP_SIGNAL_WORDS` | слова-сигналы (через запятую) |
| `CRM_ENABLED`, `CRM_PORT`, `CRM_TOKEN` | веб-CRM: включение, порт, пароль-гейт |
| `GUARD_ENABLED`, `GUARD_LLM` | защита: вкл/выкл, LLM-классификатор |
| `REMINDERS_ENABLED`, `REMINDER_TICK_SEC`, `REMIND_AFTER_MIN`, `REMIND_DAY2`, `REMIND_DAY3`, `REMIND_CLOSE_MIN` | напоминания об оплате |
| `SCHED_HOUR_UTC`, `SILENCE_DAYS_1/3/7`, `MIN_TOUCH_GAP_HOURS` | расписание/пороги догрева |

## 9. Деплой (PaaS-контейнер, напр. Amvera/Heroku-аналог)

- **Один процесс** (`scriptName main.py`), постоянный диск смонтирован в `/data` (SQLite).
- **Веб-CRM** отдаётся на домене проекта → в конфиге указать `containerPort: 80`, а приложению
  слушать `0.0.0.0:80`; отдельно завести бесплатный домен, если не создаётся автоматически.
- **Регион** ближе к стабильному доступу к Telegram.
- **StringSession для облака:** интерактивно ввести код в контейнере нельзя. Поэтому:
  1. локально один раз войти (телефон + код), получить файл-сессию;
  2. экспортировать её в строку (**без сетевого подключения** — только чтение файла);
  3. положить строку в `TG_STRING_SESSION` на PaaS; приложение поднимает userbot из строки.
- Секреты — переменными окружения PaaS (пометить как secret).

## 10. Нефункциональные требования

- **Безопасность:** секреты только в env; текст лида в LLM — как данные; блок инъекций;
  CRM за токеном; не логировать секреты.
- **Ресурсы:** два Telethon-клиента + веб-сервер + LLM-клиент → минимум ~0.5 ГБ RAM
  (пробные 0.1–0.13 ГБ не тянут).
- **Наблюдаемость:** структурные INFO-логи ключевых событий (логин, входящее+балл, эскалация,
  оплата, напоминание, блок-инъекция); при вопросе «почему не ответил» видно балл/фильтр.
- **Деградация:** без LLM — эвристика/шаблоны; без бота — напоминания шлёт userbot; без прайса
  — П5 без цен. Никогда не выдумывать цифры/факты.
- **Идемпотентность:** миграции БД, «часы» напоминаний, шаги догрева — без повторной отправки.

## 11. Тестирование

- **Юнит-тесты чистой логики** (без Telegram/LLM): бэнды, выбор шага догрева, тишина, парсинг
  JSON, эвристики, маршрутизация, статус-поток, лесенка напоминаний, guard, round-trip БД.
- **CLI ручной обкатки:** прогон «входящее → П1 → касание/эскалация» без Telegram.
- **Сценарии на живых лидах:** личка (весь путь до оплаты и статусов), группа (сигнальное
  сообщение), инъекция (блок+алерт), напоминания (укоротить пороги через env).
- **Безопасные дефолты при обкатке:** `DRY_RUN=1`, планировщик выключен, пока не проверено.

## 12. Эксплуатационные грабли (обязательно учесть)

- **SQLite нельзя держать в облачно-синхронизируемой папке** (Dropbox/Яндекс.Диск): блокировки
  и повреждение файла. Держать вне синка (`/data` на PaaS, отдельная папка локально).
- **Только один экземпляр userbot'а на одну сессию.** Одновременное использование одной
  сессии с двух IP → Telegram аннулирует ключ (`AuthKeyDuplicatedError`), лечится только
  свежим логином и новой StringSession. Рестарты разносить по времени; не подключать сессию
  локально, пока работает облако.
- **Инлайн-кнопки — только у бота, не у userbot'а** (ограничение Telegram): оплата/кнопки —
  в боте-кассире, куда лида уводят deep-link'ом.
- **Бот не пишет первым:** лид должен нажать Start у бота (deep-link решает это).
- **Отдельный проект PaaS не делит SQLite** с ботом → CRM и бот в одном процессе, либо общий
  Postgres.

## 13. Состав модулей (ориентир)

| Модуль | Ответственность |
|---|---|
| `main.py` | запуск (userbot + бот + CRM + фон), обработчики Режима 1/2, эскалация |
| `pipeline.py` | П1 скоринг, П5 касание, извлечение заказа, guard-классификатор, ответ о статусе, выбор шага |
| `prompts.py` | все промпты и шаблоны (единый источник правды) |
| `catalog.py` | загрузка прайса, поиск позиции, маршрутизация в отдел |
| `db.py` | SQLite: схема, миграции, лиды, заявки, очередь, сброс |
| `bot.py` | бот-кассир: deep-link, карточка оплаты, callback, «что дальше» |
| `reminders.py` | лесенка напоминаний об оплате (бот/агент) |
| `guard.py` | эвристика + оркестрация LLM-классификатора инъекций |
| `crm.py` | веб-CRM (HTTP, статусы, уведомления, сброс) |
| `config.py` | конфиг из env, безопасные дефолты |
| `login.py`, `export_session.py` | разовый логин и экспорт StringSession для деплоя |
| `tests` | юнит-тесты чистой логики |
