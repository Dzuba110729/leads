# Архитектура и план разработки: ИИ-диспетчер замерщиков

## 0. Принцип системы (важно для команды на старте)

Система строится по принципу **«LLM — оркестратор, решатель — источник истины по числам»**:

- **LLM (Claude/GPT с function calling)** — общается с диспетчером на естественном языке, понимает контекст («у Петрова сегодня заявок мало, добавь ему что-нибудь с Юга»), решает, какие инструменты вызвать, объясняет результат человеческим языком, обрабатывает нестандартные ситуации.
- **Расчёт маршрутов — тоже Claude, но через code execution, а не рассуждением в тексте.** Никакого стороннего VRP-движка (OR-Tools и т.п.) как отдельного сервиса нет. Claude сам пишет короткий Python-скрипт (жадная эвристика + локальные улучшения, проверка временных окон) и **выполняет** его через встроенный инструмент code execution — числа считает интерпретатор, а не догадка модели в тексте.

Это защищает от главного риска LLM-агентов в задачах с числами — уверенно звучащей, но математически неверной галлюцинации («да, замерщик успеет» — а по факту не успевает на 40 минут) — при этом весь стек остаётся «чистым ИИ»: либо Claude API в вашей системе, либо интерфейс Claude напрямую.

## 2. Инструменты LLM (function calling)

LLM не имеет прямого доступа ни к чему — только к описанным ниже функциям. Это одновременно и защита от ошибок, и способ контролировать, что именно система может делать.

| Инструмент | Что делает | Кто реализует |
|---|---|---|
| `get_orders(date, status)` | Тянет заявки из CRM за период | бэкенд-интеграция с CRM |
| `get_travel_time(from, to)` | Время в пути между точками (кэш + живой запрос к 2GIS/Яндекс Distance Matrix API) | бэкенд + внешний API |
| `optimize_routes(orders[], measurers[], constraints)` | **Главный инструмент.** Claude через code execution пишет и запускает Python-эвристику (жадный алгоритм + локальные улучшения), возвращает готовые маршруты по каждому замерщику + метрики (загрузка, опоздания, число закрытых заявок) | Claude (code execution), без внешних библиотек |
| `simulate_change(current_plan, change)` | «Что если» — пересчёт плана при точечном изменении (заболел замерщик, добавилась горящая заявка, клиент передвинул окно) | тот же принцип, инкрементальный перезапуск скрипта |
| `notify_measurer(measurer_id, route)` | Отправляет замерщику готовый маршрут | Telegram Bot API / push |
| `update_order_status(order_id, status)` | Помечает заявку как назначенную/выполненную/перенесённую | CRM API (запись обратно) |
| `get_history(measurer_id, period)` | Факт выполнения за прошлые дни — для объяснений диспетчеру и калибровки буферов времени | БД |

**Принцип:** LLM видит только эти function-контракты и их результаты. Она никогда не получает «сырую» матрицу расстояний на 15×15 и не пытается сама прикидывать маршрут — за неё это делает `optimize_routes`.

## 3. Что внутри `optimize_routes` (сердце системы)

Задача классическая — **VRPTW (Vehicle Routing Problem with Time Windows)**, но без внешнего решателя. Claude решает её сама через **code execution**: получает на вход список заявок (координаты, окна) и матрицу времени в пути, пишет Python-скрипт и выполняет его прямо в своей рабочей среде. Логика скрипта — не то, что нужно устанавливать заранее, Claude генерирует её под конкретную задачу каждый раз (и может улучшать между запусками), но по сути это:

1. **Кластеризация** заявок по географической близости (грубо — как мы вручную выделили «кусты» районов в кейсе).
2. **Жадное построение маршрута** внутри каждого кластера (nearest neighbor) с проверкой временных окон.
3. **Локальное улучшение** (2-opt — перестановка пар точек местами, если это сокращает суммарный путь и не ломает окна).
4. **Штрафы за отклонение** от мягких окон вместо жёсткого запрета — ровно как мы вручную решали, кого «подвинуть» на 30 минут; жёсткие окна — запрет без права нарушения.
5. Возврат результата в структурированном виде (JSON: маршрут по каждому замерщику, время прибытия на каждую точку, метрики) — это то, что LLM дальше пересказывает диспетчеру человеческим языком.

Время в пути в скрипт не придумывается моделью — **заранее подтягивается из 2GIS/Яндекс Distance Matrix API** отдельным вызовом и передаётся в скрипт как готовые числа (кэшируется в БД район×район, чтобы не жечь лимиты API на каждый пересчёт).

**Важно для команды:** такой подход быстрее для старта (не нужно разворачивать и поддерживать отдельный OR-Tools-сервис), но медленнее и менее гарантированно оптимален на больших объёмах (от нескольких десятков заявок и замерщиков), чем зрелый математический солвер — простая эвристика может застревать в неоптимальном решении. Для 15–30 заявок в день, как в вашем кейсе, разницы на практике почти нет; если бизнес вырастет до сотен заявок в день, к этому пункту стоит будет вернуться.

## 4. Как это выглядит для диспетчера на практике

**Утренний сценарий:**
> Диспетчер: «Распредели заявки на сегодня»
> Бот вызывает `get_orders` → `optimize_routes` → присылает: «Готово. Иванов — 6 заявок, Петров — 5, Сидоров — 4. У Петрова заявка №4 сдвигается на 25 минут позже пожелания клиента — предупредить?»

**Внештатная ситуация:**
> Диспетчер: «У Сидорова сломалась машина»
> Бот вызывает `simulate_change` (перераспределяет заявки Сидорова между Ивановым и Петровым с учётом их текущих маршрутов) → «Могу распределить 4 заявки Сидорова: 2 — Иванову (+40 мин к его дню), 2 — Петрову (+55 мин). Одна заявка (клиент с жёстким окном 12:00) не влезает ни к кому — предлагаю перенести на завтра или отдать в аутсорс. Подтверждаете?»

Здесь и раскрывается «сама принимает решения» из вашего ответа: LLM **предлагает** и после подтверждения диспетчера **исполняет** (уведомляет замерщиков, обновляет CRM) — но математику для решения ей всегда поставляет решатель, а не собственные прикидки.

## 5. План разработки (по фазам)

### Фаза 0 — Аудит данных (1–2 недели)
- Выгрузка формата заявок из CRM: обязательные поля — адрес, координаты (или адрес для геокодирования), желаемое окно клиента, тип услуги, длительность.
- Получение API-ключей 2GIS/Яндекс Distance Matrix, проверка лимитов и стоимости на объём (сколько пар точек в день реально нужно считать).
- Сверка адресов заявок с геокодером — часть адресов в CRM обычно "грязная" (опечатки, отсутствие корпуса), это чаще всего съедает больше времени, чем сам солвер.

### Фаза 1 — Голый расчёт, без диалогового слоя (2–3 недели)
- Через Claude API прогоняем вчерашние реальные заявки: на входе — список точек + окна + матрица времени в пути от 2GIS/Яндекс, на выходе — JSON с маршрутами (Claude сама пишет и выполняет скрипт через code execution).
- Сравниваем результат с тем, что реально сделал диспетчер вручную.
- Цель фазы: убедиться, что автоматический расчёт на реальных данных даёт лучшую загрузку и меньше опозданий, чем ручное распределение — это ваш "доказательный" MVP перед тем, как усложнять диалоговым слоем.
- Здесь же калибруются буферные 15 минут между заявками — по факту у разных замерщиков они разные (кто-то паркуется быстрее).

### Фаза 2 — LLM-оркестратор поверх решателя (3–4 недели)
- Подключаем Claude API с function calling, оборачиваем `optimize_routes` и остальные функции.
- Собираем Telegram-бота/веб-чат для диспетчера.
- Тестируем на "мирных" сценариях (обычное утреннее распределение) прежде чем давать LLM самой писать замерщикам.

### Фаза 3 — Обработка исключений (3 недели)
- `simulate_change`: заболевший сотрудник, горящая заявка, перенос клиента.
- Явно прописываем в системном промпте LLM: **при неопределённости — переспрашивать диспетчера, не додумывать за него** (особенно для действий с необратимыми последствиями — уведомление клиента, отмена заявки).

### Фаза 4 — Обратная связь и калибровка (постоянно)
- Замерщики отмечают факт прибытия/завершения (можно через тот же Telegram-бот).
- Система сравнивает план vs факт → пересчитывает реальные буферы, реальное среднее время замера, паттерны опозданий по районам (пробки утром/вечером).
- Это то, что вручную никто никогда не считает, а разница между "теоретическим" и "реальным" временем в пути обычно и есть главный источник срывов графика.

### Фаза 5 — Раскатка и доверие
- Первые 2–3 недели — режим "рекомендации": LLM предлагает план, диспетчер подтверждает руками каждое действие.
- Постепенно расширяем автономность: сначала автоматизируем только уведомления замерщикам, потом — точечные "что если" пересчёты, в последнюю очередь — полностью самостоятельное утреннее распределение без подтверждения.

## 6. Риски и как их закрывать

| Риск | Митигация |
|---|---|
| LLM "на глаз" прикидывает маршрут вместо вызова решателя | Жёстко в системном промпте + архитектурно: у LLM физически нет доступа к сырым координатам/матрице расстояний, только к результату `optimize_routes` |
| Лимиты/стоимость 2GIS/Яндекс API при частых пересчётах | Кэширование матрицы район×район на сутки, живой запрос — только для точек с реальным изменением плана |
| "Грязные" адреса в CRM ломают геокодирование | Отдельный шаг валидации адресов до передачи в солвер, фолбэк на ручное подтверждение диспетчером |
| LLM самовольно уведомляет клиента/замерщика без подтверждения в спорных случаях | Разделить действия на "только показать план" и "реально отправить уведомление" — второе требует явного подтверждения диспетчера, особенно на старте (Фаза 5) |
| Доверие диспетчеров к системе (саботаж/игнор) | Режим "рекомендации" в начале, показывать метрику до/после (как в нашем кейсе — загрузка выросла с ~55% до ~67%) |

## 7. Метрики успеха проекта

- **Заявок на замерщика в день** — было ~3–4, цель после внедрения — 5–6 (как в разобранном кейсе).
- **Доля продуктивного времени** (замер / (замер+путь)) — целевой ориентир 65–70%.
- **% заявок, закрытых строго в клиентское окно** — отдельно для жёстких и мягких окон.
- **Время диспетчера на утреннее планирование** — было вручную ~30–60 минут на 15 заявок, цель — секунды на первичный план + минуты на исключения.
